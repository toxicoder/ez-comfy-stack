Declined and research integrations

Third-party models and node packs evaluated for the Spark stack: the NVIDIA candidates allowed for local experimentation, the ones declined, the license on each, what you may publish from them, and the tool-by-tool verdict behind every row of the opt-in nvidia-lab tier.

What's on this page

  • The four gates - what a candidate has to clear, and which gate decided each verdict
  • Research lane - 11 NVIDIA models you may download and run locally to experiment, each with its license and its permitted use
  • Declined - the candidates that cannot run here, cannot be licensed here, or have no stated license at all
  • Dead ends - candidates that do not exist or have nothing to run, so you do not spend a day on them
  • Enforcement - how the catalog keeps the refuse list off disk and the research lane out of your downloads
  • Reopening - how to run an evaluation again when a vendor ships new artifacts
  • Per item - what it is, the blocking fact, what would reopen it, what to use instead
  • NVIDIA lab tier - the tool-by-tool verdicts on the upstream repos, container images, CLIs, install shapes, and lab graphs the opt-in tier carries, each with the catalog row that refuses it an install path

What this enables

  • Read one page instead of re-researching a candidate that was already turned, with the vendor source for each verdict
  • Tell a license wall from a hardware wall, which decides whether waiting helps
  • Know, before a 90 GB download, whether you are allowed to publish what the model prints
  • Confirm the catalog keeps refused weights off ${MODELS_DIR}, and keeps the research lane out of download-models without you auditing the list by hand
  • Confirm no nvidia-lab row reaches the image, the manifest, or Compose, and that an artifact lands only after the confirm, the headroom

GateQuestion
G1 licenseMay its weights run inside a product container, and may the outputs be used commercially?
G2 artifactIs there a linux_aarch64 artifact that installs on GB10?

A non-commercial license is not, by itself, a reason to stop you experimenting on your own box - which is why NVIDIA research models now have a research lane below instead of a flat refusal. Moving Lyra-2.0 off the refuse list relaxed one thing and did not touch the others. Running a research model without wrecking the stack

Occupancy. These do not run inside the stack's image and get no manage.sh verb. Run one at a time, in your own container or venv, with Compose down. The stack holds a one-heavy-GPU-job rule so a writer never competes with a GPU tenant for GB10 memory, and a 67 GB DiT is exactly the tenant that rule exists to keep out. Full wording: Host sidecars overview.

Every GB10 verdict above is an upstream hardware claim for other chips - H100, A100, GB200, GB300. None of these has been measured on GB10. "plausible" means nothing blocked it in principle, and is not a promise that it starts.

Declined on hardware or size

ComfyUI-DLSS5-Enhancer. Real, MIT, 327 stars, and a genuine community ComfyUI node - the only ComfyUI-native pack in this entire evaluation. It is blocked on hardware, not on policy: the worker, the ReShade carrier, and the RenoDX add-on are all Windows x86 binaries, the node gates on RTX appearing in the nvidia-smi name (GB10 does not carry it), and RTX 20 cards are refused outright. It ships no weights, so there is nothing for the refuse list to do; the NGX runtime is a third-party proprietary build the project declines to redistribute. Run it on a Windows RTX box if you want it.

ComfyUI_Nvidia_VFX_Nodes. Three nodes over NVIDIA's NGX runtime: RTXVideoSuperResolution, RTXTrueHDR, RTXVideoFrameGeneration. It installs with python -m pip install -U --no-build-isolation nvidia-vfx --index-url https://pypi.nvidia.com, and that index publishes only manylinux x86_64, win_amd64, and win_arm64 wheels. There is no linux_aarch64 wheel, so the install cannot resolve inside this image. The README's "RTX Spark is supported" line refers to the Windows-on-Arm part that win_arm64 serves; it is not evidence for DGX Spark. Two further problems on Blackwell Linux: the super-resolution node returns an all-black tensor with no exception because the bundled NGX cubins lack that architecture, and the runtime loads its own cuDNN with RTLD_GLOBAL and rewrites LD_LIBRARY_PATH, which aborts later cuDNN consumers such as the pose models. Both are open upstream. Use instead the stack's own upscaling and format nodes; run HDR and interpolation on an x86 workstation and bring the finished file back in.

NGC nre-ga. Note the name first: this is Omniverse NuRec (Neural Reconstruction), not "Neural Rendering Engine" and not "Gaussian Anything" - that last is an unrelated non-NVIDIA project. Source is open at NVIDIA/NuRec under Apache-2.0, and 26.10 is the last release published on NGC, with images renamed nre-ga to nurec-ga. nre-ga:latest is 14.29 GB compressed and its manifest is single-arch linux/amd64 on CUDA 12.8 with zero arm64 tags. The nurec-ga family that gained DGX Spark enablement returned UNAUTHORIZED to anonymous pull, so it needs an NGC account to inspect. Beyond the architecture, its input is recorded camera plus lidar NCore data, which no lane of a studio consumes.

PixelUMM, InfiniCube, GEN3C, Cosmos-Drive-Dreams are in the research lane for their license and blocked on this box for hardware or disk. The row table says which.

The NVIDIA candidates below are no longer verdicts in prose only. NVIDIA Project Lyra

Lyra is NVIDIA's open generative 3D world model line, and its two releases do not carry the same weight terms. nv-tlabs/lyra is the canonical repository for both; nv-tlabs/Project-Lyra is only the GitHub Pages site - an index.html, styles, and assets - and holds no code. The tier carries each release as its own row, so the installable half is not refused with the half that is.

Lyra 1.x is installable through the tier

Lyra 1.x generates a camera-controlled walkthrough video of a 3D-consistent world from one image. The code is Apache-2.0 and the nvidia/Lyra weights carry the NVIDIA Open Model License, which permits commercial use, so the row is opt-in and installs with bazelisk run //:manage -- nvidia-lab install lyra-1.

The cost is the run, not the license. The README reports testing on H100 and A100 only, the row budgets 80 GB of VRAM and 100 GB of disk, the Cosmos Predict 1 backbone is pulled separately, and the install builds Triton and custom kernels. No GB10 run has been reported, so treat the first one as the measurement.

Lyra 2.0 stays declined

Lyra 2.0 takes one image plus a camera trajectory, generates a walkthrough video with a 14B Wan 2.1 image-to-video

I2V

Modalities

 DiT, then reconstructs 3D Gaussian Splats from it.

Blocked on license. The nvidia/Lyra-2.0 checkpoints are released under the NVIDIA Internal Scientific Research and Development Model License. Its terms of use state that the model and any derivative "may not be distributed, deployed, sublicensed, publicly displayed, publicly performed", and that you "may not use the Model or a Derivative Model in a production environment or for the purpose of generating works for sale or distribution". Running it inside a product container is deployment. The repository code is Apache-2.0, which does not change the weight terms.

Blocked on size and hardware too. The checkpoint set is roughly 98 GB, of which about 97 GB is inference weights, including a 68 GB 32-shard DCP DiT. The maintainer reports a 48 GB card out-of-memory even with every offload flag on, and puts the practical floor near 80 GB with no quantization planned. Install is a recursive clone under conda with Python 3.10, CUDA 12.8, torch 2.7.1, and source builds of flash-attn 2.6.3 and TransformerEngine. This image is CUDA 13.0 with torch 2.14.1, so those pins would have to be reconciled by hand. Upstream targets H100 and GB200; nothing has been reported on GB10, and the attention dispatch table stops before that architecture. There are no ComfyUI nodes in the repository and no third-party wrapper.

What would reopen it. NVIDIA relicenses the nvidia/Lyra-2.0 checkpoints so deployment and production use are permitted - the row's own reopen sentence.

Use instead. A walkthrough you may actually run is the tier's lyra-1 row. Stills come from Klein and motion from Wan 2.2 and LTX-2.5, all in the pinned catalog. For 3D, the native TRELLIS lane covers image-to-3D. See NVIDIA lab, TRELLIS and 3D and Models and cache.

Nous Research Arete-27B

Arete-27B is a supervised fine-tune of a 27B Qwen text model. It is 27.4B parameters in BF16, about 54.7 GB across 18 shards, Apache-2.0 and ungated, with a 262k context. Its stated purpose is to change the political answering behavior of the base model.

Blocked on fit. It is text-generation only. Its image and video encoder is inherited and frozen, so it reads media and produces none, which leaves it no lane in a media pipeline. The stack's local model lane runs GGUF files CPU-only so a writer never competes with a GPU tenant for GB10 memory, and Arete-27B has no official GGUF release at all. Loading 54.7 GB of BF16 to rewrite a prompt sentence also breaks the one-heavy-GPU-job occupancy rule that keeps the stack stable.

Use instead. Prompt Enhance uses the pinned Qwen3-4B GGUF on CPU, the opt-in 35B pack covers the desk writer, and Qwen2.5-VL covers captioning. All three arrive with bazelisk run //:manage -- download-models. See Prompting and GGUF models.

ComfyUI_Nvidia_VFX_Nodes

This pack adds three nodes backed by NVIDIA's NGX runtime: RTXVideoSuperResolution (multi-mode upscale, denoise, deblur), RTXTrueHDR (SDR to BT.2020 HLG/PQ), and RTXVideoFrameGeneration (2-16x frame interpolation). It needs no Hugging Face download because the weights ship inside the wheel.

Blocked on architecture. The pack installs with python -m pip install -U --no-build-isolation nvidia-vfx --index-url https://pypi.nvidia.com, and that index publishes only manylinux x86_64, win_amd64, and win_arm64 wheels. There is no linux_aarch64 wheel, so the install cannot resolve inside this image. The README's "RTX Spark is supported" line refers to the Windows-on-Arm part, which the win_arm64 wheel serves; it is not evidence for DGX Spark.

Two further issues on Blackwell Linux. The super-resolution node returns an all-black tensor with no exception on Blackwell under Linux, because the bundled NGX cubins lack that architecture. The runtime also loads its own cuDNN with RTLD_GLOBAL and rewrites LD_LIBRARY_PATH, which aborts later cuDNN consumers such as the pose models. Both are open upstream.

Use instead. The image and video lanes already expose the stack's own upscaling and format nodes. Until an aarch64 wheel exists, run HDR and interpolation passes on an x86 workstation and bring the finished file back in. See Shorts and Cinema.

LuxDiT

LuxDiT estimates image-based lighting from a single photo or a video with a video diffusion transformer. It is the relighting capability the 3D lane does not have, which is why the row stays in the catalog as a card rather than disappearing.

Blocked on license. The repository ships the NVIDIA OneWay Noncommercial License, so it is the code itself, not only the weights, that bars use inside a product container. The nvidia/LuxDiT card tags the weights license:other, which is a second wall behind the first, and that tag does not read as a permission for product use.

The footprint, measured. nvidia/LuxDiT is luxdit_image/ at 11.74 GB plus luxdit_video/ at 11.74 GB plus a negligible hdr_merge_mlp/, so 23.49 GB for the whole repo. The tier row names the 11.74 GB image tree, which is what a relight run pulls; the 23.5 GB figure this section carried was the repo total, and the 21.87 GB figure the lane table carried matches neither tree and is dropped.

What would reopen it. NVIDIA relicenses the code away from the OneWay Noncommercial terms. The weight terms then have to be readable as a permission for product use, not a card tag.

Use instead. Nothing in the promoted stack relights a shot today. The 3D lane goes image to mesh with TRELLIS.2 and the Asset Bible records those outputs, so a relight stays in the DCC tools beside the stack for now. See 3D pipeline and NVIDIA lab.

InfiniCube

InfiniCube generates an unbounded voxel world with video and dynamic Gaussians for driving scenes, from a prompt and a pose.

Blocked on license. The checkpoints are hosted on a personal Hugging Face account (yifanlu/InfiniCube-checkpoints) rather than the NVIDIA org, their terms allow research and educational use only and prohibit commercial use, and they bind the user to the Waymo Open Dataset terms of service on top. The code being Apache-2.0 does not change any of that. The run is heavy as well: the Wan 14B stage is about 20 minutes per 93-frame 480p clip

dvlt (Deja View)

dvlt reconstructs multi-view geometry as pointmaps, depth, and camera poses with a looping transformer. It is the closest fit to this machine in the whole tier.

Blocked on license. The nvidia/dvlt weights are under an NVIDIA license for non-commercial research and evaluation use only, and the VGGT-derived files in the repository carry the VGGT License rather than the Apache-2.0 the rest of the tree uses. Two non-commercial terms, one on the weights and one on part of the code.

Blocked on nothing else. 0.5 GB of weights, a documented single-GPU path, 12 GB of VRAM and 5 GB of disk - the footprint a splat capture front end actually wants on one Spark. The conda pins (torch 2.5.1, CUDA 12.4) are the only other friction.

What would reopen it. The weights are relicensed for commercial use, or a permissive checkpoint of the same size appears.

Use instead. The 3dgrut row trains and renders from a COLMAP capture with no weights to license at all, and the Splat sidecar viewer reads the scenes it mints. See NVIDIA lab.

SplatPainting

SplatPainting is an interactive brush for painting and editing a Gaussian Splat scene. The editing surface is genuinely useful for the 3D lane, so the row stays as a card.

Blocked on license. The repository is Apache-2.0 except the vendored deps/gsplats tree, which carries Inria and MPII research licenses. A build that links that tree is not clean for a product image, and the disk refuse list already names Inria-3DGS for the same reason.

What would reopen it. The gsplat dependency is replaced or relicensed so a build needs no research-licensed tree.

Use instead. Scene edits belong in the DCC lane before the mesh is minted, and Splat sidecar stays a viewer that mints nothing. See DCC workflows and NVIDIA lab.

PixelUMM

PixelUMM is an encoder-free unified model that understands and generates both images and video in one network.

Blocked on footprint and on terms. The released weights are 121.63 GB of distributed checkpoints: four dirs in nvidia/PixelUMM, S8-F18-R01, S8-F19-R03, S8-F21-R02, S8-F22-R05, at 30.41 GB each (S8-F18-R01 measures 30.39), 480 .distcp shards in all, which the row rounds to 121.6. The single-checkpoint 30.41 GB figure in the lane table above is one of those four dirs, not the release. The model also pulls a 16 GB Qwen3-8B, and the documented training path asks for seven GPUs of 48 GiB or more. That is a cluster, and this stack is one Spark; the row marks GB10 unsupported. The Hugging Face card tags the weights license:other and the terms were not readable as permission for product use.

What would reopen it. A quantized single-GPU inference checkpoint with a readable permissive weight license. Both halves have to land: the footprint and the terms.

Use instead. Klein, Wan 2.2, and LTX-2.5 generate; Qwen2.5-VL captions. All of it arrives with bazelisk run //:manage -- download-models. See Prompting and Models and cache.

Cosmos Drive Dreams

Cosmos Drive Dreams generates synthetic multi-view autonomous-vehicle video and LiDAR from HD map, bounding box, and LiDAR conditions.

Blocked on architecture. The Cosmos 1 upstream it needs ships x86_64 NGC images and prebuilt CUDA wheels, so nothing resolves inside this aarch64 image. The license is not the problem here: the weights inherit the NVIDIA Open Model License from the Cosmos cards and permit commercial use. The domain is the other wall - the inputs are autonomous-vehicle sensor conditions, which no lane in this stack produces.

The weights repo, and which figures are verified. The tier row names nvidia/Cosmos-Transfer1-7B-Sample-AV, which is public (HTTP 200) with gated: "auto"; its base_model.pt measures 28.95 GB. The research-lane row above names nvidia/Cosmos-Drive-Dreams, which returns HTTP 401 to an anonymous read: it is gated, so the GB figures carried there for the models and the dataset could not be checked anonymously and are unverified.

What would reopen it. Upstream Cosmos publishes linux_aarch64 wheels or an arm64 container that runs on GB10.

Use instead. The image and video lanes. A driving-sim lane would have to exist before this row had a job. See Cinema and NVIDIA lab.

ComfyUI DLSS 5 Enhancer

This node pack pushes RGBA frames and estimated motion vectors through the DLSS 5 neural renderer and returns reconstructed frames at 1.5x to 3x. Its own code is MIT with a runtime carve-out for the bundled NVIDIA binaries.

Blocked on architecture. The pack is a client of a native D3D12 worker process that hosts ReShade, must be named nvngx.dll, and is installed by a Windows embedded-python path against a GeForce driver. There is no Linux path at all, so it cannot run in this container. That is the same NGX wall that already declines ComfyUI_Nvidia_VFX_Nodes one section above, and the same wall nvidia-lab records on the dlss5-enhancer row.

What would reopen it. NVIDIA ships a linux_aarch64 NGX runtime the pack can drive - the reopen condition the VFX nodes row waits on too.

Use instead. The stack's own upscaling and format nodes, as the VFX nodes row above says. See Shorts and NVIDIA lab.

Omniverse NuRec GA

Omniverse NuRec GA (the NGC container nre/nurec-ga) trains and serves Gaussian Neural 3DGRT and 3DGUT scenes over gRPC and renders novel views from them. The open SDK at NVIDIA/NuRec is Apache-2.0; the container is not the SDK.

Blocked on platform and on an unread license text. NVIDIA states that general Linux aarch64 is not a supported user platform, and that Grace-Blackwell enablement reaches you only through the -arm64 or -multiarch tags, which build as non-gating nightly or on-demand jobs and may not exist for a given release. Container security scanning covers x86_64 only. The floor is above 24 GB with 48 GB recommended on an R580 driver or newer. The container license text, and whether an NGC entitlement is needed to pull it at all, could not be confirmed from any public page.

What would reopen it. NVIDIA publishes a gated -arm64 or -multiarch tag for a release-branch build and states the container license and the entitlement terms in public.

Use instead. The 3dgrut row - Apache-2.0, no weights, kernels compiled on the host - trains and renders the same scene family, and the artifixer row ships a published linux/arm64 CUDA 13 image. See NVIDIA lab and its generated reference.

Gamma-World, Asset Harvester, and Instant NuRec

Three rows parked as deferred because the facts are missing rather than adverse. Gamma-World rolls out synchronized future observations and actions for several agents in one interactive world model. Asset Harvester generates simulatable autonomous-vehicle assets for simulation. Instant NuRec reconstructs a simulatable multi-camera driving world in one feed-forward pass with no per-scene training.

Blocked on missing facts. Gamma-World documents converting a released checkpoint to DCP but never says where that checkpoint is hosted, publishes no VRAM envelope, and states no weight license. Asset Harvester publishes no weight license and no GPU class. Instant NuRec is Apache-2.0 code whose README states no weight license at all, and whose uv lockfile pins are the aarch64 risk. There is nothing to size one Spark against, so the rows record the open questions instead of a guess.

Blocked on domain too. All three work in driving logs and AV assets, and no lane in this stack produces or consumes either.

What would reopen them. Each row's own reopen sentence: upstream names the weight host, states a weight license, and publishes a memory envelope. Re-check the sources list on the row before spending a day on the repository.

Use instead. gen3c is the tier's one generative row whose weights permit commercial use outright, and lyra-1 covers a walkthrough from a still. See NVIDIA lab.

Enforcement

The refuse list is fail-closed and lives in config/model-manifest.yaml, owned by the //config:policy target. A path whose name contains a refuse token is classified as a banned weight, so the disk wizard names it instead of treating it as reclaimable or as part of the keep-set. The research lane is a separate section: it never reaches the keep-set, and no verb fetches from it.

The Lyra-2.0 token stays in place, and so does Arete-27B. Lyra 1.x carries no token, because its weights are installable through the tier.

Every NVIDIA candidate above is also a row in the opt-in nvidia-lab tier, and the catalog is the enforcement. custom_nodes/ez_nvidia_lab/catalog.json is the single source of truth for each row's status, licenses, artifact, and footprint, and install and run refuse any row whose status is not opt-in before anything executes. This page is the prose behind the row; the row is what the CLI reads. The verbs and the per-row footprints are on NVIDIA lab.

Nothing in this stack downloads these weights. bazelisk run //:manage -- download-models fetches only what packs: pins, no nvidia-lab row is a manifest pack, no row is a Compose service, and no row reaches the image. An artifact lands on the host only when you run bazelisk run //:manage -- nvidia-lab install on a row whose status is opt-in, which asks for yes first, runs the host headroom preflight, refuses while a heavy occupancy mode holds the GPU, and writes under ${EZ_NVIDIA_LAB_HOME:-$HOME/.ez-comfy/nvidia-lab} - never inside the repo. The cleanup verbs default to --plan.

Reopening an evaluation

Architecture and license terms change. Re-check the primary source before you spend a day on this:

  1. Read the catalog row before the vendor page. bazelisk run //:manage -- nvidia-lab status <id> prints the status the last evaluation recorded, and plan <id> prints the artifact, the footprint, and the target an install would use. The row's gate_notes and reopen fields are the previous findings, so the day starts from them and not from zero.
  2. For an NVIDIA wheel, list the release index and confirm the exact wheel tag for linux_aarch64 and your Python ABI. A win_arm64 wheel does not prove Linux Arm support.
  3. For a checkpoint, read the license section of the model card itself and look for the words "production" and "deploy". A card tag reading Apache-2.0 can sit beside a stricter license in the body, and the repo LICENSE can cover the code while the weights sit under something else entirely - which is exactly what happened with dvlt.
  4. If the weights are on a personal Hugging Face account with no license tag, treat that as declined until the owner declares one.
  5. For a node pack, confirm it has no cloud or license-server call, since this stack is local-only.
  6. Check the hardware claim against GB10 specifically. "Tested on H100 and A100" is not "runs on Spark".
  7. Clear the refuse token in the same change that promotes the pack, with a test proving the new path works on GB10.

To promote a research model into the real catalog, clear all four gates, drop its research: row and add a packs: row in the same change, with a test proving the path works on GB10, then promote the graph with bazelisk run //:manage -- promote-workflow and update the docs in the same change. change. For a tier row the catalog edit comes first: the row's status is what makes install accept it, so a re-test that clears the four gates changes custom_nodes/ez_nvidia_lab/catalog.json, this page, and NVIDIA lab in one change, with bazelisk test //tests:bats_nvidia_lab_test green.
