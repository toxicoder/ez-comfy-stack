Symptom decision tree

Bazel ingress

bazelisk is the ingress for every test, lint, build, and docs action (Building with Bazel). These are the failures unique to that layer, before any stack or model is involved.

SymptomCauseFix
bazelisk test //:lint fails with shellcheck missing - required in CI/strict mode (apt install shellcheck or brew install shellcheck) (or shfmt, buildifier, pyright, mypy)Every gate in lints/BUILD.bazel sets REQUIRE_LINT_TOOLS=1, so a linter that is off PATH is fatal instead of printing missing - skipping and passing green. The host simply never installed that toolbazelisk run //:setup-host, or bash scripts/setup-host.sh on a host with no bazelisk yet. Confirm with bazelisk run //:setup-host -- --check. Guide: Set up a contributor host
bazelisk test //:lint is green and you suspect it checked nothingOutside the //:lint gates, scripts/lib/check_tool.sh is still resilient by design and exits 0 on a missing tool. A run that never went through //:lint can skip silentlyRun bazelisk test //:lint --test_tag_filters=manual and check it names each tool. If a tool is missing, the strict-mode line above tells you what to install
bazelisk test //:lint is green on a host you have never bootstrapped, and bazelisk run //:setup-host -- --check then exits 1 with a tools missing (N): lineThe linters were never installed on this host. A green lint result proves the gate ran, not that the tools existed - scripts/lib/check_tool.sh only asks whether a tool answers to command -vbazelisk run //:setup-host (or bash scripts/setup-host.sh where bazelisk does not exist yet), then re-run the probe and confirm it ends with every tool the Bazel targets need is on PATH at its pin. Guide: Set up a contributor host
bazelisk run //:setup-host -- --check exits 1 printing tools below pin (N): and one stale: <tool> has <got>, pin wants at least <want> (<source>) line eachA tool is on PATH but older than its pin, so the probe fails it even though it is installed. The pin source is named per line: .devcontainer/tool-versions.env for bazelisk, buildifier, shfmt and node; tests/requirements.txt for pyright and mypy. A distro tool with no pin (git, python3, shellcheck) has no floor and is never listedbazelisk run //:setup-host reinstalls the stale tools from those same pins and re-probes; on a bare host, bash scripts/setup-host.sh with no flags. If the re-probe still prints still below pin, an older copy earlier on PATH is shadowing the new one
bazelisk test //:everything (or bazelisk run //:everything) dies at its first gate with everything: gate //:setup-host -- --check failedThe bootstrap probe is gate 1 on purpose, so no analysis, test, or docs gate runs on a host that cannot lint. Any missing or stale tool trips it, and the two lines above the failure name those toolsRead the tools missing / tools below pin lines it just printed, run bazelisk run //:setup-host, then re-run. A host that cannot install anything (CI with its own toolchain step) can skip the probe with bazelisk run //:everything -- --skip-bootstrap
exec_shell: cannot locate scripts/manage.sh (RUNFILES_DIR=...) and exit 1The generated launcher from tools/exec_shell.bzl searched RUNFILES_DIR, TEST_SRCDIR, and <argv0>.runfiles and found none of them. That happens when the runfiles tree was not materialised - invoking the launcher copy in bazel-bin/ directly, or a stale output tree after a Bazel or .bazelversion changeInvoke it through Bazel (bazelisk run //:manage -- doctor), never the file under bazel-bin/. If it persists, bazelisk clean --expunge and re-run
scripts/lib/paths.sh: No such file or directory, or a bazelisk run //:manage -- <verb> that dies before printing anythingmanage.sh sources lib/paths.sh by dirname "$0". Under a plain sh_binary the executable sits alone in bazel-bin/ while its data is in <target>.runfiles/, so the sibling is missing. //scripts:manage is an exec_shell target precisely so script and data land in runfiles side by sideRun via bazelisk run //:manage -- <verb> so the launcher resolves the runfiles copy. Do not bash the bazel-bin/ copy. bazelisk clean --expunge clears a runfiles tree left stale by a Bazel upgrade
run-utility: utility name must be a bare name under scripts/utilities///scripts:run-utility takes a bare utility name, not a path. A scripts/utilities/ prefix, a / in the name, or a .sh suffix is rejected so the target cannot be pointed outside that directoryDrop the path and the suffix: bazelisk run //scripts:run-utility -- download-limit status, not -- scripts/utilities/download-limit.sh status
bazelisk test //tests:owned_files_check fails naming a fileA first-party source file is not claimed by any target's srcs / data / filegroup, so it would silently stop being built and lintedAdd the file to the owning package's BUILD.bazel (or the filegroup that covers it). The guard is in //:test-fast, so it also fails the default gate
bazelisk run //:everything prints ==> //:everything: SKIP docs-site visual lane (the Docker daemon is not reachable), or (no committed baselines under docs-site/tests/visual/goldens), and finishes with all gates passed (1 skipped: ...)Gate 4 compares Playwright screenshots inside the pinned container, so it needs a reachable Docker daemon and committed baselines. Either one missing is an environment gap, and the sweep reports it rather than failing a gate the host cannot runStart Docker, or capture the baselines with bazelisk run //docs-site:visual-linux -- --update, review the image diff, and commit it. The lane is never silently dropped: bazelisk test //:test-all runs both visual targets unfiltered
bazelisk test //docs-site:visual_tooling_test fails with desktop: no committed baseline for <page>The visual guard enumerates the pages docs-site/tests/visual/site.spec.mjs captures and demands a committed PNG for each under docs-site/tests/visual/goldens/. Nothing has been captured on this checkout, or a new page landed without its baselinebazelisk run //docs-site:visual-linux -- --update renders the whole set in the same image CI uses (Docker required). Review the added images before committing; a host capture differs in font metrics and reports every page as changed later
bazelisk test //tests:pytest fails with run_pytest: python3 cannot import pytest_cov; refusing to run the suite unmeasured (or pytest on the same line)The 100% floor is measured by pytest-cov. A host that never installed the pinned Python tools used to run the suite with no coverage flag at all and still report green; the runner now stops and names the repair insteadbazelisk run //:setup-host, or python3 -m pip install -r tests/requirements.txt, then re-run. CI installs that same pin as part of its lint-tools step, so a runner that skipped it fails here rather than passing unmeasured
bazelisk test //tests:pytest fails inside test_coverage_gate.py with unmeasured first-party Python (join COV_SCOPE or GATED_ELSEWHERE): [...], COV_SCOPE names <tree>, which holds no production Python, or tests/.coveragerc omits <pattern>, which is not a test moduleThe auditor keeps the floor honest: a new package arrived outside every measured tree, a tree in scope was renamed or emptied, or an omit rule started hiding production code. Any of those lets coverage report a flattering number while real code goes untestedAdd the tree to COV_SCOPE in the pytest runner and give //tests:pytest its sources in data, or name the Bazel target that already measures it in GATED_ELSEWHERE. Drop a stale omit line instead of widening one. Rationale: Building with Bazel
bazelisk test //lints:mypy prints Explicit "Any" is not allowed [explicit-any]mypy.ini sets disallow_any_explicit = True for production Python, so Any has to be a declared boundary rather than a convenience. The pytest tree is checked separately by mypy-tests.ini under a committed ledger, which lifts the rule for test fakesReplace it with a TypedDict, a Literal, object, or a TYPE_CHECKING alias of the real third-party class (ImageTensor: TypeAlias = "torch.Tensor"). A genuine third-party boundary gets a [mypy-<module>] section with disallow_any_explicit = False plus a row in the boundary table of Strong types; work that is merely unfinished gets the same section with disable_error_code = explicit-any and goes on the debt ledger
bazelisk test //lints:mypy prints Missing type arguments for generic type "dict" [type-arg] (same shape for list, set, tuple, Callable)disallow_any_generics = True: a bare container means Any in its parameters, which is the broad type in disguiseWrite the parameters (dict[str, int], Callable[[str], None]). For a genuinely open payload reuse the named aliases in custom_nodes/ez_common/ (Json, JsonObject, ComfyInputTypes) instead of inventing a fresh dict[str, Any]
bazelisk test //tests:python_tests fails inside test_strong_types.py with explicit Any outside a declared boundary or debt module naming files, or with mypy.ini exempts these modules ... delete the section, or with the budget is NThe AST inventory is the config-independent backstop, so it runs where mypy is not installed: it flags any Any in production whose module mypy.ini exempts as neither a boundary nor a debt module, it flags an exemption that no longer carries Any (a dead section silently licenses the next one), and it ratchets PRODUCTION_ANY_BUDGET, PRODUCTION_CAST_BUDGET, and DEBT_MODULE_BUDGETRepair the annotations the same way as the [explicit-any] row. When a sweep legitimately lowers a count, lower that budget in the same commit - all three only ever move down. Delete a section that the second message names
bazelisk test //lints:mypy_tests or //lints:pyright_tests prints ... ratchet failed: with a has N diagnostics, baseline allows M lineThe pytest tree is held to the same type law as production but carries a backlog, so each lane compares per-file diagnostic counts with its committed ledger (lints/mypy_tests_baseline.json, lints/pyright_tests_baseline.json). A file that grew, or a new test file with no entry, fails the gateNarrow what the test hands a production signature (assert isinstance, or a typed helper) rather than raising a baseline number or widening the signature to suit the fake. When a file genuinely drops to zero, set its entry to 0 in the same commit - the gate fails a clean file whose baseline is still nonzero
bazelisk test //lints:js_types prints JS typecheck ratchet failed: with a has N diagnostics, baseline allows M linetsc --checkJs type-checks the custom-node frontends against their JSDoc and compares per-file diagnostic counts with lints/js_types_baseline.json. A file that grew, or a new .js with no entry, fails the gateFix the JSDoc: a type expression on every @param / @returns, and a real @typedef {object} where the tag says {object}. Raising a baseline number is the wrong fix. When a file genuinely drops to zero, set its entry to 0 in the same commit - the gate fails a clean file whose baseline is still nonzero
bazelisk test //lints:js_types prints tsc missing - required in CI/strict modeThe gate type-checks the frontends with the TypeScript the docs-site lockfile pins, so it needs that install, and //:lint sets REQUIRE_LINT_TOOLS=1, which turns a missing tool into a failure instead of a skipbazelisk run //docs-site:install - the same npm ci --legacy-peer-deps the docs job and the CI core job run before the lint lane. A tsc on the PATH also satisfies the gate when the checkout carries none, but the pinned compiler is what keeps the counts comparable with lints/js_types_baseline.json
